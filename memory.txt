name: feedback-cma-es-narrow-passage-limits
description: "CMA-ES/evolutionary optimization is a poor fit for discovering narrow-passage maneuvers from scratch; works only as a tightly-anchored local refiner, and even then the anchor's exact waypoints must not be over-constrained"
metadata:
  type: feedback
---

CMA-ES (and evolutionary/continuous optimizers generally) cannot discover a
feasible path through a maze-like narrow corridor from scratch — verified
across many hours on [[project-bus-hairpin-cma-es-investigation]]. It reliably
gets stuck at whatever point requires the first genuinely tight maneuver,
regardless of population size, generations, restarts, or K (segment count).

**Why**: sampling-based/grid-search planners (Hybrid A*) explore the
combinatorial structure of "which side to hug, when to reverse" step by step;
smooth continuous optimizers have no gradient signal connecting "this
direction is progress" from "this direction hits a wall 2m in" across a
winding boundary — most of the space between start and goal is blocked.

**How to apply**: don't reach for CMA-ES/genetic algorithms as the primary
tool for constrained path-planning discovery in tight/narrow environments.
It *can* work as a **local refiner** on top of an already-feasible path from
a discrete planner (Hybrid A*, RRT*, etc.) — but only if:
1. The refinement window is anchored to *exact* entry/exit poses from the
   known-good path, with a hard box constraint around the seed's own gene
   values (not just a small sigma0 — CMA's adaptive step-size still runs
   away within tens of generations in high-dim chained-arc representations,
   since early-segment perturbations compound through every later segment).
2. Never trust an "improved" candidate that only passed the fast/simplified
   boundary check — always re-verify against the full-precision boundary
   before accepting; a candidate can look better under a simplified boundary
   while being strictly worse under the true one (confirmed: violation
   dropped in fast-eval terms while switches ballooned 28→71 under precise
   re-check).
3. **Don't anchor to one exact intermediate waypoint+heading** pulled from
   the source path when a genuinely different (e.g. wider-swing) strategy
   might legitimately rejoin the corridor at a *different* point. Anchoring
   to a single fixed exit pose forces the search back into
   variations-compatible-with-the-original-path even when it has full
   freedom otherwise (confirmed: a wide-loop re-search achieved violation=0
   everywhere yet never got within 3m of the exact fixed exit pose/heading —
   not a feasibility problem, an over-constrained-target problem). The
   correct fix (not yet implemented) is a *corridor/range* target (e.g.
   "anywhere along this straight run, heading within X° of its tangent")
   rather than one exact point.
4. If pure CMA-ES is stuck around the same fitness across restarts/K with
   no variance, check whether **random sampling alone** (no CMA at all) can
   beat it — confirmed CMA got stuck at pos_err~3m across 20+ restarts/K
   combos on a local sub-window while plain uniform random sampling (20k
   draws) found pos_err=0.10m immediately. This points to CMA converging
   into a bad local basin on a fitness landscape made discontinuous by a
   switch-count penalty term, not to the target being unreachable — when
   this happens, use random-search-then-narrow-CMA-polish instead of pure
   CMA-ES.

See also [[feedback-dont-conclude-infeasible-too-early]] (same family of
lesson: a search's failure to find something is not proof it doesn't exist).

## 2. 시도한 방법과 결과 (시간 순)

### 2-1. 처음부터 CMA-ES로 전역 탐색 — 실패
`evolutionary.py`의 `search()`: K를 1부터 늘려가며(웜스타트), 각 K에서 몇 차례 재시작. 처음엔 목표까지 직선거리를 fitness로 썼는데, 진입/진출 경사로가 굽어 있어(reference_path.py가 이미 경고한 문제) 직선거리가 줄어드는 방향이 벽을 가로지르는 함정에 갇혀 K를 8까지 늘려도 목표오차가 전혀 안 줄었다. `reference_path.remaining()`(중심선 투영 진행률)으로 바꿔 이 함정은 해소했지만, 근본 문제는 남았다: **경로의 약 70% 지점(하이브리드 A*가 25~28회 방향전환을 써야 했던 그 좁은 헤어핀 포켓)에서 45번(K=1~15, 3회 재시작)의 시도 전부가 멈췄다.** 그 지점을 넘으려면 좁은 구멍을 정확히 뚫는 특정한 다중 방향전환 조합이 필요한데, 무작위 변이 기반 탐색으로는 그런 조합을 우연히 찾을 확률이 사실상 0에 가깝다.

**결론**: 이런 좁은 통로 문제는 애초에 조합적 탐색(그리드 A*)이 필요한 문제지, 매끄러운 연속최적화로 처음부터 찾을 문제가 아니다.

### 2-2. 기존 Hybrid A* 경로를 원호로 재파라미터화 + CMA-ES 웜스타트 — 실패
이미 검증된(위반 0) 403노드 경로를 (곡률,길이) 구간 열로 근사 변환해 CMA-ES 출발점으로 쓰는 방법. 두 가지 실제 버그를 발견/수정했다:

1. **헤딩 wrap 오류**: 런의 총 회전량을 `(끝 theta - 시작 theta)`를 `(-π,π]`로 wrap해서 구했는데, 39m짜리 최장 런은 180도 넘게 돌 수 있어 winding을 잃고 완전히 틀린 평균곡률이 나왔다(재구성 위치오차 90m). 인접 노드 간(각 에지 ~0.3m로 작아 모호성 없음) 헤딩차를 런 안에서 누적하는 방식으로 수정.
2. **후진 구간 부호 오류**: `kappa = acc_dtheta / acc_len`으로 계산했는데, `arc_pose_at`은 `dtheta = kappa * 부호달린_길이`로 적분하므로 REV 구간(sign=-1)마다 헤딩변화가 반대로 재구성됐다(재구성 시 goal_heading_err가 청크 크기와 무관하게 항상 정확히 같은 값으로 고정되는 것으로 발견). `kappa = sign * acc_dtheta / acc_len`으로 수정.

두 버그를 고친 뒤 재구성 오차는 극적으로 줄었지만(위치오차 90m→0.96m), **원본 해상도(0.3m)와 동일하게 쪼개도(K=402) 위반면적이 19m² 밑으로 안 내려가는 재구성-고유 오차 바닥**이 있음을 확인했다 — 원본이 오일러 적분(6-substep)으로 만들어진 경로라, 그걸 정확한 원호로 재피팅하는 방식 자체의 구조적 한계.

CMA-ES로 이 잔여 위반을 지역 정제하려 했으나, **사슬형 민감도 문제**를 실측으로 확인했다: 구간이 순차로 이어붙는 구조라 이른 구간의 아주 작은 변화가 뒤쪽 전체에 누적/증폭돼, `sigma0=0.03`·전역 `[-1,1]` bounds인 채로 CMA-ES를 50세대만 돌려도 위반면적이 seed의 27m²에서 3300m²로 폭주했다. 대응책으로:
- seed±box_eps 하드 클립 bounds 도입 (전역 sigma0로는 못 막힘, 물리적으로 벗어날 수 없게 박스 자체를 제한)
- **회귀 방지 가드**: CMA-ES는 x0 자체를 후보로 평가하지 않으므로(1세대는 x0 주변 표본일 뿐), 안전영역이 좁으면 "이번 배치에서 그나마 나은 것"이 seed 자체보다 나쁠 수 있다(실측: violation 27.7→233.7). seed의 fitness를 기준선으로 깔고 이보다 못하면 seed로 되돌리는 안전장치 추가.
- **단순화 폴리곤 함정**: fast-eval(단순화+안쪽버퍼 폴리곤) 기준으로만 비교했더니, 그 폴리곤에서는 seed보다 좋아 보이지만 정밀 재검증하면 오히려 나쁜(위반↑, switches 28→71) 후보가 "개선"으로 잘못 채택됐다. 이후 모든 채택 기준을 정밀(원본) 폴리곤 재평가로 바꿈.
- **길이 유전자 부호 고정**: box_eps만으로는 짧은 구간이 넉넉한 절대폭 안에서 쉽게 부호(기어)가 뒤집혀 새 방향전환을 만들어냈다(28→71). 길이 유전자가 0을 못 건너가게 하드 클립해 switches가 seed보다 절대 늘 수 없게 만듦.

이 모든 안전장치를 갖춘 뒤에도 **CMA-ES는 단 한 번도 seed를 넘어서는 해를 찾지 못했다** — 여러 restart/chunk_len 조합으로 반복 확인.

### 2-3. 국소 방향전환 제거 (성공, 최종 결과물)
접근을 바꿨다: 경로 전체를 하나의 유전자 벡터로 다루지 않고, 28개 방향전환 경계 각각에 대해 "이 전환 하나만 없앨 수 있는가?"를 독립적으로, 아주 낮은 차원(≤6)의 지역 CMA-ES로 검사(`try_connect`). 그 전환을 감싸는 두 런의 시작/끝 pose를 원본 데이터에서 그대로 고정(anchor)하고, 그 사이를 단일 기어로 잇는 경로를 찾아 성공(위반 0 + 끝 pose 정합)하면 그 구간만 교체.

- 초기 구현은 매 `try_connect` 호출마다 원본 16,391정점 경계 폴리곤을 `prepare()`해서, 28개 스위치의 작은 예산(maxiter=50, restart=1) 테스트조차 937초 걸렸다. 단순화+안쪽버퍼 폴리곤으로 탐색하고 성공 후보만 정밀 재검증하는 방식(다른 파일들과 동일 패턴)으로 바꿔 15배(937s→61s) 단축.
- 28개 중 **3개**(switch 8, 10, 15 — 전부 1~7노드짜리 아주 짧은 "보정" 구간)가 제거 가능했고, 서로 겹치지 않아 전부 적용. 전체 440노드 경로를 원본 정밀 폴리곤으로 재검증해 위반 0건, 목표오차 0.0005m 확인 후 저장.
- 나머지 25개(대부분 헤어핀 팁 근처 1.6m×2.6m 안에 몰려있음)는 짧은 것들이 이미 제거된 걸 보면 실제로 기하학적으로 필요한 방향전환일 가능성이 높다는 가설.

### 2-4. 밀집 클러스터(20회 방향전환) 통째 재탐색 — 실패
try_connect(2런/고정기어)보다 넓은 재구조화가 가능한지 확인하려고, 헤어핀 팁의 밀집 구간(런 3~23, 20회 방향전환) 전체를 자유 기어 CMA-ES(`search_cluster`)로 재탐색.

- 첫 시도(K=16,12,9,7 × 5재시작 × maxiter=350): **위반은 항상 0인데 위치오차가 3~4.5m대에 고정**되어 전혀 안 줄었다(K를 늘려도, 재시작을 바꿔도 동일). 무작위 샘플 20,000개만으로 pos_err=0.10m를 즉시 찾아, **CMA-ES가 벽 때문이 아니라 스위치-카운트 페널티가 만든 불연속 지형에서 나쁜 국소해에 갇힌 것**으로 진단.
- 대응: 넓은 탐색은 병렬 무작위 샘플링에 맡기고 CMA-ES는 그 결과 주변 좁은 박스만 다듬는 "무작위탐색→국소정제" 방식으로 전환. 초기 예산(1만 샘플)은 분산이 너무 커 재현이 안 됐고, 예산을 40만/K로 올렸더니 K=16 하나에만 36분+ 걸려 중단.

### 2-5. 사용자 제시 참고 예시 — 넓게 스윙하는 실제 기사님 주행 패턴
사용자가 "실제 기사님들은 좁게 여러 번 방향전환하지 않고 루프 가운데 공간을 크게 돌아서 정점 근처에서 한두 번만 전환한다"는 예시 이미지를 제시. 소스를 찾아보니 `outputs/final_start_goal.png`(시작/목표 박스만 있고 경로선은 없음) 위에 사용자가 직접 그린 예시 스케치로 확인됨 — 저장된 실제 데이터는 아니지만, 방향(넓은 스윙 전략) 자체는 타당한 가설.

### 2-6. 충돌모델 재검토 — 바퀴 vs 차체 (중요, 부분 반영)
사용자 지적: "버스 차체 전체가 경계를 넘으면 안 되는 게 아니라 바퀴가 넘으면 안 된다." 확인 결과:
- 경계 폴리곤은 DXF "밑 도면"(바닥/평면 도면) 레이어에서 온 것 — 벽이 아니라 **포장 노면 가장자리**의 평면도로 보임. 이는 "차체가 넘으면 안 됨"보다 "바퀴가 노면 안에 있어야 함" 해석에 더 부합.
- 그런데 지금까지 이 프로젝트 전체(RL 환경, Hybrid A*, 이번 CMA-ES 작업 전부)는 **차체 범퍼 기준**(뒷축→앞면 d_ref=9.06m, 앞 오버행 2.77m 포함)으로 충돌을 검사해왔다. 실제 앞바퀴는 축거 L=6.29m 지점에 불과해, 지금까지 모델은 앞바퀴보다 2.77m 더 나간 범퍼까지 경계 안에 있으라고 요구해온 셈.
- 뒷 윤거 실측치가 config.yaml에 없어(앞 윤거 T_f=2.075m조차 "추정치"), 사용자와 상의해 **폭은 보수적으로 차체 전폭(2.495m) 유지, 길이만 축거 기준(front_oh=L=6.29m, rear_oh=0)으로 변경**하기로 확정.
- 이 수정을 반영해 2-4의 넓은 창(루프 전체, 25회 방향전환 구간)을 재탐색했더니 **모든 K, 모든 시도에서 위반=0** — 즉 수정된 모델 하에서는 루프 폭이 실제로 병목이 아니었다는 뜻. 다만 목표(도착 pose)를 원본 경로가 우연히 도착했던 정확한 한 점+방향으로 고정해놨던 게 새 병목으로 드러남(아래).
- **이 수정은 이번 CMA-ES 탐색 스크립트(`repair_loop.py`/`repair_cluster.py`)에만 적용했고, `bus_hairpin_env.py`/`hybrid_astar.py` 등 공유 모델은 건드리지 않았다.** 재개 시 프로젝트 전체에 적용하는 게 유효한 다음 단계.

### 2-7. 넓은 스윙 재탐색 (수정된 모델) — 실패, 원인은 다름
2-6의 수정된 모델로 루프 전체(노드 131~267, 25회 방향전환) 재탐색을 70분(4199.6초) 돌렸다. **위반은 전 구간에서 0**이었으나, 정확한 도착 pose(위치+방향)에 tol 이내로는 끝내 도달하지 못함(최선: K=3, 방향전환 2회, 위치오차 3.1m, 방향오차 22°).

**진단**: exit pose를 원본 hybrid A* 경로가 우연히 그 좁은 전략으로 도착했던 정확한 한 점+헤딩으로 고정해뒀다. 그 뒤로 이어지는 130노드짜리 긴 직진 구간은 어디서 합류해도(방향만 맞으면) 되는데, "정확히 이 한 점"으로 못박은 게 넓은 스윙 전략의 발견을 막았다. 올바른 수정은 목표를 "정확한 한 점"이 아니라 "이 직진 구간 어디든, 방향만 그 구간 접선과 맞으면 OK"인 **범위/코리도어 타겟**으로 재설계하는 것 — 미구현.

사용자가 여기서 투자 대비 효율을 고려해 중단을 결정, 2-3의 26회 전환 결과를 최종으로 확정.

## 3. 핵심 교훈 (재사용 가능한 일반 원칙)

1. **CMA-ES/진화적 최적화는 좁은 통로가 있는 미로형 경로계획을 "처음부터" 푸는 데 안 맞는다.** 시작과 목표 사이 대부분의 공간이 벽으로 막혀 있으면, 매끄러운 fitness 그라디언트가 "이 방향이 맞다"는 신호를 줄 수 없다. 이미 뚫린 경로(그리드 탐색 등)를 국소적으로 다듬는 용도로만 쓸 것.
2. **국소 정제도 "seed 근방 박스"로 하드 제한해야 한다.** sigma0를 아무리 작게 잡아도, 사슬형(순차 적분) 파라미터화에서는 이른 구간의 변화가 뒤로 누적/증폭되어 CMA-ES의 스텝사이즈 적응이 수십 세대 안에 폭주할 수 있다.
3. **정제 결과는 반드시 seed와 정밀 폴리곤 기준으로 비교해 "절대 원본보다 나빠지지 않게" 보장해야 한다.** 단순화 폴리곤 기준 "개선"은 정밀 기준으로 후퇴일 수 있다(실측: 위반 27.7→233.7, 스위치 28→71).
4. **CMA-ES가 여러 재시작/K에서 똑같은 값에 고정되면, 먼저 순수 무작위 샘플링으로 벽인지 지형(landscape) 문제인지 구분할 것.** 이번에 무작위 샘플 2만 개가 CMA-ES 350세대×5재시작보다 훨씬 나은 해를 즉시 찾았다 — 불연속 페널티 항(방향전환 수 등)이 CMA-ES를 나쁜 국소해에 가두는 경우가 있다.
5. **국소 창을 "원본 경로의 정확한 한 점"에 anchor하면, 그 점과 호환되지 않는 근본적으로 다른 전략(예: 넓은 스윙)은 애초에 찾을 수 없다.** 진입/진출 조건은 가능하면 정확한 pose가 아니라 범위/코리도어로 정의해야 한다.
6. **충돌 검사 풋프린트가 무엇을 표현하는지(벽 vs 노면 가장자리, 차체 vs 바퀴) 도면 출처까지 확인할 것.** 이번 프로젝트는 "밑 도면"(평면도) 레이어에서 경계를 뽑았는데도 처음부터 차체 범퍼 기준으로 검사해왔다 — 이 가정이 문제 난이도 자체를 실제보다 부풀렸을 가능성이 있다.

## 4. 여전히 유효한 것 (재확인 불필요)

- Hybrid A* 403노드 참조경로(`geometry/reference_path.json`) 자체는 원본 정밀 폴리곤 기준 위반 0으로 이미 검증되어 있고, 이번 세션의 모든 결과가 이걸 기준선(seed)으로 삼았다. 이번에 발견된 재구성 버그(헤딩 wrap, REV 부호)는 **제 재파라미터화 코드의 버그**였지 원본 경로 자체의 결함이 아니다.
- `simulation/geometry/reference_path_repaired.json`(28→26회)은 원본 정밀 폴리곤 기준으로 완전히 재검증되어 안전하게 채택 가능하다.

축거(wheelbase) L = 6.290m (DXF 실측).

제 CMA-ES 원호 표현도 똑같습니다 — 한 구간(segment) 안에서는 곡률(kappa)이 상수로 고정되고, 다음 구간으로 넘어갈 때 곡률이 임의로 바뀔 수 있습니다. 즉 "천천히 핸들 돌리면서 주행"이 아니라 "한 각도로 고정해서 쭉 가다가, 멈춰서 다음 각도로 바꾸고 다시 감"을 표현합니다.

저수준 bicycle 모델(kinematics/bicycle.py)도 조향각속도(delta의 변화율)와 가속도(v의 변화율)가 완전히 분리된 별도 입력이라, v=0인 상태에서 delta만 바꾸는 것(제자리 조향)이 물리적으로 허용됩니다 — 실차에서 "dry steering"(제자리에서 핸들 꺾기)이 가능한 것과 같습니다.

딱 하나 정확히 모델링 안 하는 부분: 제자리에서 핸들을 완전히 꺾는 데 걸리는 실제 시간(steer_rate_max=0.5 rad/s 기준, 중립→풀락 약 1.4초)을 하이브리드 A*/제 CMA-ES는 "공짜"로 취급합니다 — 경로의 기하학적 형태(충돌 여부, 방향전환 횟수)에는 영향이 없지만, "이 기동이 실제로 몇 초 걸리나"는 두 방법 다 최적화 대상에 넣지 않았습니다. RL 쪽은 dt=0.1s 단위로 실제 스텝을 밟으니 이 시간이 자연히 반영되긴 합니다.

## 0. 한 줄 요약 (TL;DR)

**지금 경로의 방향전환 26회 중 절대다수는 "지형이 강제한 것"이 아니라 두 가지 인공물이다: (1) 실제보다 2m 더 넓게 잡은 차체(범퍼) 충돌모델, (2) 고정 원호 격자탐색의 이산화 한계.** 미분기하 이론(Reeds–Shepp)은 장애물 없는 공간에서 전·후진 차량의 최단경로가 **방향전환 2회 이하**임을 보장한다 — 26 대 2의 격차는 대부분 제거 가능하다는 뜻이다.

**결정적 근거(이번에 실측):** 바퀴 기준 U턴 필요폭 **21.0m** < 개방 회차구역 실폭 **21.9m** → **넓은 U턴이 물리적으로 들어간다.** 바디 기준은 25.0m가 필요해 안 들어간다. 즉 사용자가 지적한 "여러 번의 전후진"은 대체로 **잘못된 충돌모델이 강제한 것**이며, 이를 바로잡으면 실제 기사님 예시(넓게 한 번 스윙)에 가까운 소수(단자리) 방향전환 경로가 나올 개연성이 크다.

---

## 1. 왜 지금 경로가 최적이 아닌가 — 3가지 근본 원인

### 1-1. 기준 경로(Hybrid A*)가 애초에 "전역 최적"이 아니다
현재 `hybrid_astar.py`는 **고정 길이(0.3m) 원호 프리미티브**를 21개 조향각으로 뻗어가며 비용(거리 + 후진페널티 + 전환페널티)을 낮추는 격자탐색이다. 두 가지 구조적 약점:

- **Reeds–Shepp 해석적 확장이 없다.** 표준 Hybrid A*(Dolgov–Thrun)는 매 노드에서 "현재 자세→목표를 장애물 없이 잇는 RS 곡선"을 시도하는 *analytic expansion*을 핵심 요소로 갖는다. 이게 있으면 격자 운에 기대지 않고 목표에 정확히·깔끔하게(cusp 최소로) 도달한다. 현재 구현엔 이게 없어서, 목표 근처에서 격자를 잘게 쪼개 우연히 맞히는 식이라 도착부가 지저분하고 방향전환이 과하다.
- **양방향 탐색의 접합(`_find_meeting`)은 최적성을 보장하지 않는다.** g비용 합 최소 접합점을 고르지만, 이는 satisficing(그럴듯한 해)이지 증명된 최적해가 아니다.

### 1-2. 충돌모델이 실제보다 2m 더 빡빡하다 (가장 큰 레버)
`_bus_polygon`은 뒷축→앞**범퍼**(d_ref=9.06m, 전방오버행 2.77m 포함)까지의 차체 전체 사각형을 경계 안에 가둔다. 그러나 실제 제약은 **바퀴가 노면(밑 도면=포장 평면도)을 벗어나지 않는 것**이다(사용자 지적, `cma_es_investigation` 리포트 §2-6). 앞바퀴는 뒷축에서 L=6.29m — 범퍼보다 2.77m 안쪽이다. 이 차이가 회전 기하 전체를 바꾼다(§2).

### 1-3. 국소 수정은 나쁜 "골격"을 못 고친다
이번 세션의 개선(28→26회)은 전부 기존 경로 좌표를 anchor로 고정한 국소 편집이라, **어느 쪽 벽에 붙어 어떻게 도는지(골격)는 원본과 동일**하다. 벽에 붙어 잘게 꺾는 골격 자체가 문제인데, 그걸 놔둔 채 잔가지만 쳐낸 셈이다. 사용자가 보는 "쓸모없는 공간 + 반복 전후진 + 긴 거리"는 전부 이 골격에서 나온다. **골격을 새로 계획해야(re-plan) 하지, 다듬어선(repair) 안 된다.**

## 2. 결정적 발견 — 바퀴 vs 바디 = "U턴이 되냐 안 되냐"

뒷축 중심 회전반경 R=7.37m, δ_max=40.5° 기준 (모두 실측 검증):

| 항목 | 바디(범퍼) | 바퀴(타이어) | 차이 |
|---|---|---|---|
| 외측 스윕 반경 | 12.51 m | **10.50 m** | **−2.01 m** |
| 내측 스윕 반경 | 6.70 m | 6.33 m | −0.37 m |
| 스윕 밴드 폭 | 5.81 m | **4.17 m** | −1.64 m |
| **U턴 필요폭 (2×외측)** | **25.0 m** | **21.0 m** | **−4.0 m** |

**개방 회차구역(경계 폴리곤 x>2 영역) 실측: 21.9 m(가로) × 17.5 m(세로).**

→ **바퀴 모델: 21.0m 필요 < 21.9m 가용 → 넓은 U턴 성립(아슬아슬).**
→ **바디 모델: 25.0m 필요 > 21.9m 가용 → U턴 불성립 → 다점 K턴 강제.**

이게 스모킹건이다. 현재의 20+회 방향전환은 "이 도로가 원래 그렇게 좁아서"가 아니라 **범퍼를 벽으로 취급해서 U턴 공간을 4m 깎아먹은 결과**다. 범퍼 오버행은 실제로 포장 경계선 바깥(연석/사면 위 허공)으로 넘어가도 무방하다 — 바퀴만 노면에 있으면 된다. 이걸 반영하면 회차구역에서 넓은 스윙 U턴이 열린다.

(주의: 2×외측반경은 "완전한 회전원이 들어갈 공간"이라는 보수적 기준이다. 실제 U턴(반원)은 이보다 덜 필요할 수 있어, 바퀴 모델의 여유는 계산보다 더 클 가능성이 높다. 정확한 값은 §3 재계획이 밝힌다.)

## 3. 제안 설계 — 3계층 (모델 교정 → 위상 재계획 → 연속 정제)

실제 자율주행/자동주차 플래너의 검증된 2단계(탐색으로 위상 결정 → 최적화로 매끈하게)를, 이 문제의 모델 교정을 앞에 붙여 3계층으로 구성한다.

### Layer 1 — 충돌모델을 바퀴 기준으로 교정 (프로젝트 전체)
- 충돌 판정 형상을 **차체 사각형 → 4개 타이어 접지점(또는 이를 감싸는 축거×윤거 사각형)**으로 교체. 길이는 뒷축→앞축 L=6.29m, 뒤는 뒷축(0) 또는 뒷오버행 대신 뒷바퀴 위치. 폭은 사용자 확정대로 보수적으로 전폭(2.495m) 유지(뒷 윤거 실측 확보 시 T_r로 정밀화).
- 적용 위치: `bus_hairpin_env.py`의 `_bus_polygon`/`_collision_at`, `hybrid_astar.py`의 `_bus_polygon`, 그리고 검증 스크립트들. **이번 세션엔 신규 CMA-ES 스크립트에만 부분 적용했으나, 이번엔 공유 모델에 정식 반영한다.**
- 선택: 범퍼 오버행이 경계를 넘는 것을 명시적으로 허용하되, "장애물(실제 벽/기둥)"이 별도로 정의되면 그건 차체 전체로 검사(오버행이 실제 구조물엔 부딪히면 안 되므로). 현재 obstacles.json은 비어 있어 당장은 노면 경계만 문제.

### Layer 2 — 위상 재계획: Reeds–Shepp Hybrid A* (골격을 새로 찾음)
- **RS 해석적 확장 추가**: 매 확장 노드에서 목표까지 RS 곡선(전·후진·직선 조합, cusp≤2)을 해석적으로 계산해 장애물(바퀴 기준) 없으면 즉시 연결. RS 곡선은 **구성상 cusp 최소**라, 방향전환을 사후 페널티로 억제하는 게 아니라 원리적으로 적게 만든다.
- **방향전환을 비용의 1순위로**: gear_switch_penalty를 거리 대비 훨씬 크게(예: 전환 1회 = 거리 15~20m 등가) 잡아, "멀리 돌더라도 전환을 줄이는" 사용자 선호를 직접 반영. 경사 구간 전환은 기존 slope 가중 유지.
- **목표는 정확한 한 점 그대로**(사용자 요구: 앞면중심이 위 경사로 캡에 닿고 전진 도착). 단, tol_pos=0.5m·tol_heading=0.1rad 여유 활용. — 과거 `repair_loop` 실패는 *중간 접합점*을 한 점으로 못박은 탓이었는데, 전구간 재계획은 그 인공 접합이 없어 이 문제가 원천 소멸.
- 시작 자세를 좁은 격자 대신 RS로 확장하면 §1-1의 이산화 인공물도 사라진다.
- 출력: 골격(어느 쪽으로 스윙, cusp 몇 회·어디, 대략 곡률열).

**교차검증용 해석적 구성(선택):** 개방구역에 들어가는 최대 회전원(바퀴 R_out=10.5m)을 하나 배치하고, 그 원을 두 경사로 중심선에 접선(Dubins/RS)으로 잇는 구성을 손으로 계산 → "이 도로에서 이론상 최소 cusp가 몇인지"의 독립적 기준선을 얻는다. RS-Hybrid-A* 결과가 이 기준선과 일치하면 최적에 가깝다는 강한 방증.

### Layer 3 — 연속 정제: 다중슈팅 NLP (CMA-ES가 아니라)
Layer 2가 준 골격(cusp 개수·순서 고정)의 **연속 파라미터만** 매끈하게 최적화.

- **왜 CMA-ES가 실패했나 = 단일슈팅 + 미분프리.** 구간을 시작점부터 순차 적분(single shooting)하면 이른 구간의 섭동이 뒤 전체에 누적돼 조건수가 최악이 된다(실측: 50세대에 위반 27→3300m²). 미분프리라 이 악조건을 극복할 그라디언트 정보도 없다.
- **해법 = 다중슈팅(multiple shooting) + 그라디언트 기반 NLP.** 각 노드 자세 `(xᵢ,yᵢ,θᵢ)`를 독립 변수로 두고, 이웃 노드 사이 "유효 원호로 연결" 연속성 제약을 **결함(defect) 등식**으로 건다. 그러면 한 노드의 섭동이 이웃에만 영향 → Jacobian이 **띠(banded)** 구조 → 조건수 양호. 이게 CMA-ES가 못 넘은 벽을 넘는 핵심 기술적 전환이다.
- 목적함수: 총길이 + 곡률변화율²(부드러움). 방향전환 항은 위상 고정이라 상수.
- 제약: |κ|≤κ_max, 각 샘플의 바퀴 사각형이 경계 안(부호거리≥0, soft penalty 또는 hard). 시작·목표 자세 고정.
- 솔버: **scipy `minimize(method="SLSQP")`**(venv에 scipy 1.16 확인됨, 수백 변수까지 유한차분 그라디언트로 충분). 더 크면 CasADi+IPOPT(자동미분) 검토 — 단, 설치 필요.

## 5. 검증 계획 (숫자만 믿지 말 것 — 반복 학습된 교훈)
1. **바퀴 스윕 포락선 시각화**: 최종 경로의 매 자세에서 4바퀴 접지 사각형 합집합을 그려 노면 경계 안에 있는지 육안 + 면적 위반=0 확인.
2. **범퍼 오버행 별도 표기**: 오버행이 경계를 넘는 구간을 다른 색으로 표시해 "의도된 허용"임을 명시(실제 구조물과 겹치지 않는지도 함께).
3. **cusp 지점의 경사·정지 타당성**: 각 방향전환이 급경사(하부 램프 8.24%)에 있지 않은지 확인(정지 후 재출발 난이도).
4. **해석적 구성과 대조**(§Layer2): RS-A* cusp 수 ≈ 해석적 기준선인지.
5. **R_min 민감도**: R_min(10.5m)·T_f(2.075m)가 "추정치"이므로 ±10% 흔들어 해가 질적으로 유지되는지 스윕.

## 6. 리스크 · 불확실성 · 폴백
- **R1: 바퀴 모델이 물리적으로 정당한가?** 경계가 정말 "노면 가장자리"이고 그 바깥이 넘어가도 되는 공간(연석/사면)인지 최종 확인 필요. 만약 경계 바깥이 곧 낭떠러지/벽이면 오버행도 못 넘으므로 바디 모델이 맞다. → **도면 출처(밑 도면 레이어의 실제 의미) 확인이 선행**. 아니면 폭만 바퀴, 길이는 절충 등 중간안.
- **R2: 21.9 vs 21.0은 아슬아슬하다.** 여유 0.9m는 오차·안전마진에 취약. 넓은 U턴이 0-cusp로 안 되고 2~6 cusp가 될 수 있다 — 그래도 26→단자리는 큰 승리. **0 cusp를 약속하지 않는다.**
- **R3: RS-Hybrid-A* 구현/RS 곡선 구현 부담.** OMPL 등 외부 라이브러리는 Windows 설치가 번거로움 → RS 곡선(≈300줄, 문서화 잘 됨)을 인하우스 구현. 리스크 있으나 1회성.
- **R4: NLP 수렴 실패 가능성.** SLSQP가 큰 문제에서 정체하면 (a) 문제를 cusp 구간별로 쪼개 풀거나 (b) IPOPT로 승급. Layer 2 골격이 이미 실현가능(feasible)하므로 최소한 그 골격은 항상 폴백으로 남는다(절대 원본보다 나빠지지 않음 — 이번 세션 내내 지킨 원칙).
- **폴백 사다리**: Layer1만 해도(바디→바퀴) 기존 Hybrid A* 재실행으로 상당한 개선 기대 → Layer2 추가 → Layer3 추가. 각 단계가 독립적으로 가치 있고, 앞 단계 결과가 최소 보장선이 된다.

## 7. 순서와 예상 노력
1. **(선행·저비용) 경계 의미 확인 + Layer 1 적용**: 바퀴 풋프린트를 공유 모델에 반영하고, *현행* Hybrid A*를 그대로 재실행. — 이것만으로 "U턴이 열린" 효과를 즉시 관찰(가설 검증). 반나절.
2. **Layer 2**: RS 곡선 + 해석적 확장을 Hybrid A*에 추가, 전환비용 상향, 재탐색. 해석적 구성으로 기준선 확보. — 1~2일.
3. **Layer 3**: 다중슈팅 NLP 정제기 구현(SLSQP), 골격 위에 매끈화. — 1~2일.
4. 각 단계 후 §5 검증 + 시각화로 사용자 확인.

**권장 시작점: 1번(Layer 1 + 현행 A* 재실행).** 가장 싸고, "바퀴 모델이면 넓은 U턴이 실제로 열리는가"라는 이 계획 전체의 핵심 가설을 가장 빨리 실증하기 때문. 여기서 기대대로 방향전환이 급감하면 2·3번의 정당성이 확고해지고, 아니면(경계가 진짜 벽이면) 조기에 방향을 재검토할 수 있다.

def _rect(x, y, theta, front_oh, rear_oh, half_w):
    c, s = math.cos(theta), math.sin(theta)
    local = [(front_oh, half_w), (front_oh, -half_w), (-rear_oh, -half_w), (-rear_oh, half_w)]
    return Polygon([(x + lx * c - ly * s, y + lx * s + ly * c) for lx, ly in local])


def main():

    # 바퀴 기준 footprint: 앞=앞축(L), 뒤=뒷축(0), 폭=전폭(보수적).

    fine_steer = tuple(round(-1.0 + 0.1 * i, 2) for i in range(21))

        footprint=wheel_fp,
        delta_max=env.model.delta_max,

        tol_pos=0.6,
        tol_heading_deg=12.0,
        obstacle_polygons=env.obstacle_polygons,
        debug=True,
    )

    start = (env.start_x, env.start_y, env.start_heading)
    goal_rear_x = env.goal_x - env.d_ref * math.cos(env.goal_heading)
    goal_rear_y = env.goal_y - env.d_ref * math.sin(env.goal_heading)
    goal = (goal_rear_x, goal_rear_y, env.goal_heading)

    print("start", start, "goal", goal, flush=True)
    t0 = time.time()

    body_viol = 0   # 범퍼가 연석을 넘는 노드 수 = 바퀴모델이 '풀어준' 양
    for (x, y, theta, gear) in path:

            wheel_viol += 1
        if not env.boundary_polygon.contains(_rect(x, y, theta, *body_fp)):
            body_viol += 1
    print(f"wheel-model violations (should be 0): {wheel_viol}")
    print(f"body-model violations (범퍼가 연석 넘는 노드 = 구모델이 금지했던 것): {body_viol}")

LAYERS = {
    "ROAD_BOUNDARY":      {"color": 8},   # 회색
    "PATH_REAR_FWD":      {"color": 5},   # 파랑 (뒷축, 전진)
    "PATH_REAR_REV":      {"color": 1},   # 빨강 (뒷축, 후진)
    "PATH_FRONTAXLE_FWD": {"color": 4},   # 시안 (앞축, 전진)

    "START_GOAL":         {"color": 3},   # 초록 (시작/목표 자세)

def split_runs(rear_wps, gears):
    """gears[i]는 노드 i로 들어오는 에지(i-1->i)의 기어(gears[0]은 시작 더미).
    같은 기어가 이어지는 최대 구간(run)들로 노드를 나눈다. 각 run은 경계
    노드를 이웃 run과 공유한다(끊긴 폴리라인이 cusp에서 만나도록)."""
    n = len(rear_wps)
    if n < 2:
        return []
    edge_gears = gears[1:n]
    runs = []
    k = 0
    m = len(edge_gears)
    while k < m:
        g = edge_gears[k]
        j = k
        while j < m and edge_gears[j] == g:
            j += 1
        runs.append((k, j, g))  # 노드 k..j (포함), 기어 g
        k = j
    return runs


def rect_pts(x, y, theta, front, rear, half_w, scale):
    c, s = math.cos(theta), math.sin(theta)
    local = [(front, half_w), (front, -half_w), (-rear, -half_w), (-rear, half_w)]
    return [((x + lx * c - ly * s) * scale, (y + lx * s + ly * c) * scale) for lx, ly in local]

    msp.add_lwpolyline(bpts, close=True, dxfattribs={"layer": "ROAD_BOUNDARY"})

    # --- 뒷축/앞축 경로: 방향별 구간 폴리라인 ---
    def front_axle(x, y, th):
        return (x + L * math.cos(th), y + L * math.sin(th))

    runs = split_runs(rear_wps, gears)
    for (k, j, g) in runs:
        seg = rear_wps[k:j + 1]
        rear_line = [(x * scale, y * scale) for (x, y, th) in seg]
        fa_line = [(fx * scale, fy * scale) for (x, y, th) in seg for (fx, fy) in [front_axle(x, y, th)]]
        rear_layer = "PATH_REAR_REV" if g == "REV" else "PATH_REAR_FWD"
        fa_layer = "PATH_FRONTAXLE_REV" if g == "REV" else "PATH_FRONTAXLE_FWD"
        msp.add_lwpolyline(rear_line, dxfattribs={"layer": rear_layer})
        msp.add_lwpolyline(fa_line, dxfattribs={"layer": fa_layer})

    # --- 방향전환 지점 마커 ---
    marker_r = (env.model.L * 0.15) * scale
    for i in range(1, len(runs)):
        k = runs[i][0]
        x, y, th = rear_wps[k]
        msp.add_circle((x * scale, y * scale), marker_r, dxfattribs={"layer": "GEAR_CHANGE_PTS"})

    # --- 시작/목표 자세: 차체 외곽(범퍼 기준) 실루엣 + 라벨 ---
    for label, (x, y, th) in [("START", rear_wps[0]), ("GOAL", rear_wps[-1])]:
        body = rect_pts(x, y, th, d_ref, rear_oh, half_w, scale)
        msp.add_lwpolyline(body, close=True, dxfattribs={"layer": "START_GOAL"})
        # 진행방향 표시선(뒷축 -> 앞면)
        fx, fy = x + d_ref * math.cos(th), y + d_ref * math.sin(th)
        msp.add_line((x * scale, y * scale), (fx * scale, fy * scale), dxfattribs={"layer": "START_GOAL"})
        txt = msp.add_text(label, height=marker_r * 1.5, dxfattribs={"layer": "START_GOAL"})
        txt.set_placement((x * scale, y * scale))

    out_path = SIM_DIR / args.out
    doc.saveas(out_path)

    n_switch = len(runs) - 1
    total_len = sum(
        math.hypot(rear_wps[i][0] - rear_wps[i - 1][0], rear_wps[i][1] - rear_wps[i - 1][1])
        for i in range(1, len(rear_wps))
    )
    print(f"입력: {args.path_json}  (노드 {len(rear_wps)}개, 방향전환 {n_switch}회, 길이 {total_len:.1f}m)")

    print(f"구간(run) 수: {len(runs)}  ->", ", ".join(f"{g}:{j-k}노드" for (k, j, g) in runs))
    print("레이어:", ", ".join(LAYERS.keys()))
    print(f"저장: {out_path}")


if __name__ == "__main__":
    main()

def _wrap(a):
    return (a + math.pi) % (2 * math.pi) - math.pi


def body_polygon(x, y, theta, front, rear, half_w):
    c, s = math.cos(theta), math.sin(theta)
    local = [(front, half_w), (front, -half_w), (-rear, -half_w), (-rear, half_w)]
    return Polygon([(x + lx * c - ly * s, y + lx * s + ly * c) for lx, ly in local])


def densify(rear_wps, substeps=4):
    """인접 뒷축 자세 사이를 substeps로 선형(각도는 wrap)보간해 스윕 틈을 없앤다."""
    out = []
    for i in range(len(rear_wps) - 1):
        x0, y0, t0 = rear_wps[i]
        x1, y1, t1 = rear_wps[i + 1]
        dt = _wrap(t1 - t0)
        for k in range(substeps):
            f = k / substeps
            out.append((x0 + (x1 - x0) * f, y0 + (y1 - y0) * f, t0 + dt * f))
    out.append(tuple(rear_wps[-1]))
    return out


def add_geom(ax, geom, **kw):
    """shapely (Multi)Polygon을 구멍까지 반영해 채워 그린다."""
    polys = geom.geoms if geom.geom_type == "MultiPolygon" else [geom]
    for poly in polys:
        verts, codes = [], []
        for ring in [poly.exterior, *poly.interiors]:
            cs = list(ring.coords)
            verts.extend(cs)
            codes.extend([MplPath.MOVETO] + [MplPath.LINETO] * (len(cs) - 2) + [MplPath.CLOSEPOLY])
        ax.add_patch(PathPatch(MplPath(verts, codes), **kw))

진출구간은 현재 좌측통행(왼쪽여유 3.7m << 오른쪽여유 6.7m)이다. 진출로
'중간 구간'의 왼쪽(진행방향 기준 좌측)에 keep-out 띠를 obstacle로 넣어
버스를 오른쪽으로 민다. 시작(포켓 탈출)·도착(캡 중앙) 부근은 keep-out을
비워 자유롭게 둔다. 목표점(경사로 끝단 중앙)은 고정.

def split_runs(rw, gears):
    n = len(rw); edge = gears[1:n]; runs = []; k = 0; m = len(edge)
    while k < m:
        g = edge[k]; j = k
        while j < m and edge[j] == g:
            j += 1
        runs.append((k, j, g)); k = j
    return runs


def _longest_line(geom):
    if geom.geom_type == "LineString":
        return geom
    return max(geom.geoms, key=lambda g: g.length)


def build_keepout(exit_xy, road_poly, offset_right, trim_head, trim_tail):
    """진출 경로의 중간부를 오른쪽으로 offset_right 옮긴 median 을 기준으로,
    그 왼쪽(남쪽) 도로 영역을 keep-out 폴리곤으로 만든다."""
    line = LineString(exit_xy)
    Lm = line.length
    mid = [line.interpolate(s).coords[0]
           for s in [Lm * t for t in [trim_head + (1 - trim_head - trim_tail) * i / 40 for i in range(41)]]]
    midline = LineString(mid)
    # 오른쪽으로 옮긴 median: offset_curve 부호는 진행방향 기준. 미드포인트가
    # 더 '오른쪽'(진행 heading-90도 쪽)이 되는 부호를 실측으로 고른다.
    cand = []
    for dist in (offset_right, -offset_right):
        try:
            oc = _longest_line(midline.offset_curve(dist))
            cand.append((dist, oc))
        except Exception:
            pass
    # 진행방향 기준 오른쪽인지 판정: 미드 지점에서 heading-90 방향과 옮긴 방향의 내적
    i = len(mid) // 2
    hx, hy = mid[i + 1][0] - mid[i - 1][0], mid[i + 1][1] - mid[i - 1][1]
    rn = (math.sin(math.atan2(hy, hx)) * -1, math.cos(math.atan2(hy, hx)) * -1)  # heading을 -90도 회전(우측)
    best = None
    for dist, oc in cand:
        mp = oc.interpolate(oc.length / 2).coords[0]
        dv = (mp[0] - mid[i][0], mp[1] - mid[i][1])
        dot = dv[0] * rn[0] + dv[1] * rn[1]
        if best is None or dot > best[0]:
            best = (dot, oc)
    median = best[1]
    # median의 왼쪽 반평면(단측 버퍼)을 도로와 교차 -> keep-out
    left_region = median.buffer(200.0, single_sided=True)  # single_sided 양수=왼쪽
    keepout = left_region.intersection(road_poly)
    return keepout, median


def add_geom(ax, geom, **kw):
    polys = geom.geoms if geom.geom_type == "MultiPolygon" else [geom]
    for poly in polys:
        if poly.is_empty:
            continue
        verts, codes = [], []
        for ring in [poly.exterior, *poly.interiors]:
            cs = list(ring.coords)
            verts += cs
            codes += [MplPath.MOVETO] + [MplPath.LINETO] * (len(cs) - 2) + [MplPath.CLOSEPOLY]
        ax.add_patch(PathPatch(MplPath(verts, codes), **kw))

"""우측통행(keep-right) — 진출 구간(run4)을 플래너로 다시 풀지 않고, 이미
검증된 경로를 진행방향 오른쪽으로 '옆으로 밀어' 우측통행으로 만든다.

Hybrid A*로 진출을 재계획하면 시작(포켓 탈출) 지점에서 거친 격자로는 트리가
죽고(closed_a=348 고정) fine 격자는 느리다. 진출 경로 자체는 이미 유효하니,
포즈를 진행방향 오른쪽으로 offset 만큼 이동(시작·목표는 taper로 0 유지)하고
바퀴 충돌·곡률(R_min)만 재검증한다. 훨씬 빠르고 확실하다.
"""
import argparse
import json
import math
from pathlib import Path

import matplotlib
import matplotlib.pyplot as plt
from shapely.geometry import Polygon

from envs.bus_hairpin_env import BusHairpinEnv

matplotlib.rcParams["font.family"] = "Malgun Gothic"
matplotlib.rcParams["axes.unicode_minus"] = False
SIM_DIR = Path(__file__).resolve().parent.parent


def _wrap(a):
    return (a + math.pi) % (2 * math.pi) - math.pi


def split_runs(rw, gears):
    n = len(rw); edge = gears[1:n]; runs = []; k = 0; m = len(edge)
    while k < m:
        g = edge[k]; j = k
        while j < m and edge[j] == g:
            j += 1
        runs.append((k, j, g)); k = j
    return runs


def smoothstep(t):
    t = max(0.0, min(1.0, t))
    return t * t * (3 - 2 * t)


def taper(u, ramp, tail):
    """u∈[0,1]. 시작(0)~ramp 구간 0→1, 중간 1, (1-tail)~끝 1→0."""
    if u < ramp:
        return smoothstep(u / ramp)
    if u > 1 - tail:
        return smoothstep((1 - u) / tail)
    return 1.0


def main():
    ap = argparse.ArgumentParser()
    ap.add_argument("--offset-right", type=float, default=2.0, help="진출 오른쪽 이동량[m]")
    ap.add_argument("--ramp", type=float, default=0.35, help="시작부 taper 비율(포켓탈출 구간은 안 밀도록 크게)")
    ap.add_argument("--tail", type=float, default=0.15, help="도착부 taper 비율")
    ap.add_argument("--out-json", default="geometry/reference_path_keepright.json")
    ap.add_argument("--out-png", default="outputs/keepright_exit.png")
    args = ap.parse_args()

    env = BusHairpinEnv()
    L, half_w = env.model.L, env.half_width
    kappa_max = 1.0 / env.model.R
    d = json.load(open(SIM_DIR / "geometry" / "reference_path_wheelmodel.json", encoding="utf-8"))
    rw = d["rear_waypoints"]; gears = d["gears"]
    runs = split_runs(rw, gears)
    a4 = runs[-1][0]
    exit_poses = [tuple(p) for p in rw[a4:]]

    # arc-length
    s = [0.0]
    for i in range(1, len(exit_poses)):
        s.append(s[-1] + math.hypot(exit_poses[i][0] - exit_poses[i - 1][0],
                                    exit_poses[i][1] - exit_poses[i - 1][1]))
    Ltot = s[-1]

    # 오른쪽으로 이동 (진행방향 heading의 -90도 = 우측)
    shifted = []
    for i, (x, y, th) in enumerate(exit_poses):
        u = s[i] / Ltot if Ltot > 0 else 0.0
        off = args.offset_right * taper(u, args.ramp, args.tail)
        rx, ry = math.sin(th), -math.cos(th)  # heading -90도 (우측)
        shifted.append([x + off * rx, y + off * ry])
    # 시작/목표는 정확히 유지
    shifted[0] = [exit_poses[0][0], exit_poses[0][1]]
    shifted[-1] = [exit_poses[-1][0], exit_poses[-1][1]]

    # heading 재계산(옮긴 폴리라인 접선), 끝점은 원본 유지
    new_exit = []
    for i in range(len(shifted)):
        if i == 0:
            th = exit_poses[0][2]
        elif i == len(shifted) - 1:
            th = exit_poses[-1][2]
        else:
            th = math.atan2(shifted[i + 1][1] - shifted[i - 1][1],
                            shifted[i + 1][0] - shifted[i - 1][0])
        new_exit.append([round(shifted[i][0], 3), round(shifted[i][1], 3), round(th, 6)])

    # 곡률 검사
    max_kappa = 0.0
    for i in range(1, len(new_exit)):
        ds = math.hypot(new_exit[i][0] - new_exit[i - 1][0], new_exit[i][1] - new_exit[i - 1][1])
        if ds > 1e-6:
            dth = abs(_wrap(new_exit[i][2] - new_exit[i - 1][2]))
            max_kappa = max(max_kappa, dth / ds)
    print(f"진출 노드 {len(new_exit)}, 길이 {Ltot:.1f}m, offset {args.offset_right}m")
    print(f"최대 곡률 {max_kappa:.4f} (한계 {kappa_max:.4f}) -> {'OK' if max_kappa <= kappa_max * 1.05 else '초과! ramp 늘리거나 offset 줄일 것'}")

    # 접합 + 바퀴 충돌 검증
    new_rw = [list(rw[i]) for i in range(a4)] + new_exit
    new_gears = gears[:a4] + ["FWD"] * len(new_exit)

    def wheel_poly(x, y, th):
        c, sn = math.cos(th), math.sin(th)
        loc = [(L, half_w), (L, -half_w), (0.0, -half_w), (0.0, half_w)]
        return Polygon([(x + lx * c - ly * sn, y + lx * sn + ly * c) for lx, ly in loc])

    viol = sum(1 for (x, y, th) in new_rw if not env.boundary_polygon.contains(wheel_poly(x, y, th)))
    n_switch = sum(1 for i in range(1, len(new_gears)) if new_gears[i] != new_gears[i - 1])
    total_len = sum(math.hypot(new_rw[i][0] - new_rw[i - 1][0], new_rw[i][1] - new_rw[i - 1][1])
                    for i in range(1, len(new_rw)))
    print(f"접합 후: 노드 {len(new_rw)}, 방향전환 {n_switch}, 길이 {total_len:.1f}m, 바퀴위반 {viol}")

        # reduce offset on sharp original curved pocket, but do not reduce at the final approach.
